# CodeArts / Loomy 完整请求链路对比（2026-11-19）

本次复现了 Loomy 的两处路由缺陷：模型 ID 大小写未校正、账号模型权限未参与选号。
它们会让 DeepSeek 请求实际运行 Spark，产生与准确 ID 直连不同的耗时。单凭首字接近总耗时不能判断整个网关在缓冲。

## 后续修正：首字前阻塞与后台余额

上一版在请求开始时等待整个账号池目录加载，3 个账号一批、每批最多 10 秒；大池慢端点会叠加成几十秒甚至数分钟。
回归用例复现了这一点。现在整个池只等统一 10 秒总预算，并复用同一轮加载，超时后可以使用已取得的健康账号目录。
这只是目录准备阶段上限，不能当作整个推理请求的首字保证。

按用户要求取消每日/永久积分优先级。推理只调用共享余额缓存的同步 `peek()`，不调用 `readStale/readOne/refreshOne`，不查询或等待余额端点。
复用上游已有每 60 秒后台刷新器；缓存确认积分用尽时跳过账号，缓存未知且允许永久积分时可尝试业务请求。
永久积分锁定且缓存不能确认每日余额时立即返回 503，保持原锁定约束。缓存更新后，下一次选号/队列轮询直接读取新结果。

补齐上游响应头等待的超时：复用 `DSH_LOOMY_FIRST_TOKEN_TIMEOUT_MS`（默认 120 秒），到期中止并换号，普通失败仍最多尝试 3 次。
响应头到达即撤销这个计时，后续流式读取仍由原生 SSE 首字/块间隔超时管理；成功长流不会因响应头预算到期而被取消。

当前版本全量 218 项测试通过，格式、lint、类型检查和前后端构建通过。
编译产物冒烟确认 `/healthz`、`/admin` 及后台每 60 秒余额刷新器正常启动。
慢端点回归使用模拟传输；本次尚未连接用户服务器验证其真实网络。

## 完整链路

两渠道都走以下入口，Chat、Responses、聚合与直连网关复用同一调度接入：

```text
客户端 / sub2api
  → Express /v1（调用方鉴权；反代到回环网关）
  → 上游 OpenAI 网关（请求解析；模型路由；LLM runtime）
  → 宿主 scheduled-adapter（完整流租约；输出前换号；取消；背压）
  → 渠道调度（候选账号；会话绑定；在途名额）
  → 上游渠道 adapter（消息转换；认证；发请求；SSE 解析）
  → LLM 内容块 → 网关 SSE → Express 增量转发 → 客户端
```

| 环节 | CodeArts | Loomy | 本次处理 |
| --- | --- | --- | --- |
| 入口与流式反代 | `gateway.controller.ts`，`Readable.fromWeb().pipe()` | 相同 | 无全量响应收集，沿用增量转发 |
| 调度生命周期 | `scheduled-adapter.ts`，完整流结束才释放 | 相同 | 共用取消、背压、输出前重试和输出后禁止重放 |
| 账号与缓存 | 账号绑定；稳定 Chat-Id / 正文缓存键；独立任务 Session-Id | 账号绑定；按会话和实际账号生成 `prompt_cache_key` | 保留绑定和缓存键；仅在真正换号时重建 |
| 模型目录 | 上游 CodeArts 目录，模型 ID 为小写 | 各账号目录不同，DeepSeek / GLM ID 含大写 | Loomy 改为按账号缓存真实目录，模型列表取并集 |
| 选号 | 按模型冷却、在途与会话窗口选择 | 原先只按冷却、在途、余额等选择，未核对账号是否提供目标模型 | Loomy 只选目录包含目标模型的账号 |
| 发送模型 ID | 小写 CodeArts ID | 原先可原样发送小写 ID，上游可能成功回退 Spark | 按所选账号目录写入准确 ID；无目录依据不发送 |
| 发送前余额 | 无 Loomy 的每日/永久积分分档 | 只读后台更新的共享缓存，不查询或等待端点 | 去掉积分档位优先级，保留永久积分锁与手动顺序 |
| 本地容量 | 默认每号 3 在途，并保留已验证的华为 60 秒会话占位 | 默认每号 2 在途，无华为保留窗口 | 保留两渠道独立规则，界面可热更新 |
| 上游受限 | 队列/会话容量、HTTP/SSE 信号 | 429、积分耗尽、认证失败等 | 保留分类换号；Loomy 大小写别名共享模型冷却 |
| SSE 与首字 | 原生 CodeArts SSE 解析器 | 原生 Loomy SSE 解析器 | 不更改解析协议；测试确认推理与正文可在结束前到达客户端 |
| 记账 | 按实际所选账号计量 | 相同 | 日志模型名是请求路由，不能证明上游实际执行模型 |

相关实现：`src/modules/gateway/gateway.controller.ts`、`src/host/scheduled-adapter.ts`、
`src/host/codearts-scheduling.ts`、`src/host/loomy-scheduling.ts`、`src/host/loomy-models.ts`。
供应商协议、模型解析、缓存实现与凭据读取仍复用锁定依赖，未修改依赖或复制其推理协议。

## 同账号实测：大小写可以改变实际运行的模型

使用用户授权的账号 B4（仅为测试顺序别名，不保存身份信息），同一提示词：
“按顺序列出1到30，逗号分隔。不要解释。”，`max_tokens: 512`、`stream: true`、`reasoning_effort: none`。
两次都直连 Loomy，读取原始 SSE 的 `model` 字段，不以网关回写模型名作为证据。

| 发出的 ID | 实际 SSE 模型 | 响应头 | 首推理 | 首正文 | 完整响应 |
| --- | --- | ---: | ---: | ---: | ---: |
| `DeepSeek-V4.1-Flash` | `DeepSeek-V4.1-Flash` | 2.212 s | 2.365 s | 5.888 s | 5.958 s |
| `deepseek-v4.1-flash` | **`spark-x2.6`** | 20.227 s | 20.242 s | 25.413 s | 25.680 s |

这证明大小写错误可让“同名模型”的请求走向不同后端。数值是单次对照，并非吞吐统计或延迟保证。
`none` 在请求中得到保留；即使如此，上游仍可能产生 reasoning，不能承诺一定关闭其内部思考。

另一个修复前样本中，上游响应头本身等了 **39.151 秒**，网关客户端收到响应头为 **39.516 秒**；
上游首正文 39.767 秒、客户端首正文 40.116 秒。该样本实际也是 Spark。
同一请求内的上下游时间线表明，约 39 秒发生在等待上游响应，而非 Express 攒完整正文。
不能把不同请求的耗时相减当作网关开销。

## 账号权限实测

对本次提供的 28 个账号分别查询官方 `GET /api/v1/models`：

- 8 个目录提供 DeepSeek / GLM：B4、B7、B10、B13、B16、B22、B25、B27。
- 16 个目录只提供 `spark-x2.6-low` 与 `spark-x2.6-4b`。
- 4 个目录返回凭据失效或账号停用：B2、B3、B14、B19。

提供模型不代表有积分：B7 的目录正常，但推理请求返回 HTTP 402，仍需要已有额度换号机制。
之前的“请求成功”统计没有记录原始 SSE 模型身份，不能据此认定每个账号都支持 DeepSeek。

## 修复后真实网关复测

外部仍发送小写 ID，传输边界确认发送准确 ID；成功请求的原始 SSE 模型也与准确 ID 相同：

| 入口 / 账号 | 外部请求模型 | 原始 SSE 模型 | 上游首推理 / 客户端首推理 | 上游首正文 / 客户端首正文 | 客户端完成 |
| --- | --- | --- | ---: | ---: | ---: |
| Express 代理 / B10 | `loomy/deepseek-v4.1-flash` | `DeepSeek-V4.1-Flash` | 9.861 / 9.876 s | 23.709 / 23.723 s | 23.812 s |
| Express 代理 / B10 | `loomy/glm-5.3-flash` | `GLM-5.3-Flash` | 6.737 / 6.747 s | 10.487 / 10.497 s | 10.999 s |
| 28 账号混合池 / B4 | `loomy/deepseek-v4.1-flash` | `DeepSeek-V4.1-Flash` | 1.497 / 1.664 s | 5.583 / 5.749 s | 5.983 s |
| 28 账号混合池 / B13 | `loomy/deepseek-v4.1-flash` | `DeepSeek-V4.1-Flash` | 4.713 / 5.258 s | 11.046 / 11.590 s | 12.275 s |

混合池实际只派发到提供 DeepSeek 的 B4、B13、B16，没有派发到 Spark 专属账号。
本轮 8 次测量中 4 次完成，另 4 次触发测试客户端的 30 秒超时，其中包括直连上游 B10；
更早一次直连 B4 也遇到 90 秒超时。**模型回退已修正，上游长尾没有因此消失**，不能用成功样本宣称统一加速。
本轮成功响应没有报告缓存命中，不能据此估算真实缓存收益。

28 账号刷新后的成功目录没有逐请求重新查询；另有 4 个失败目录在 15 秒短缓存到期后各重查一次。
模拟缓存测试另外验证了热目录零网络查询、并发加载去重、手动刷新与 token 替换。

## 修复行为与缓存边界

按账号与 token 摘要缓存真实目录，成功 TTL 沿用上游 20 分钟，失败短缓存 15 秒，同账号并发查询复用在飞请求。
冷目录最多并行查询 3 个账号，整个池共享 10 秒总预算；热目录不新增网络查询。
冷启动或目录过期时仍需等待权限查询，账号很多或端点故障会增加这部分延迟。
手动/后台刷新使目录重新读取，更换 token 自动失效，移除/禁用账号时清除旧权限。

外部 `loomy/deepseek-v4.1-flash` 可以继续使用，发给上游前转换为账号目录中的 `DeepSeek-V4.1-Flash`。
只接受准确匹配或唯一的大小写别名；已知账号均不支持时停止发送，返回 404；目录无法确认时返回 503。
支持该模型的账号均在冷却时返回 429，即使池中还有空闲 Spark 账号。
没有新增对话结果缓存，提示词和明确传入的思考档位不会被这次映射改写。
