# CodeArts 首字延迟实测（2026-11-18）

本文保留当时的测试配置。后续已将冷却调整为随机 1–3 分钟，并修复缓存键和满载粘性迁移；
当前行为见 [调度与缓存核对记录](codearts-scheduling-review-2026-11-18.md)。

使用用户提供的两个 CodeArts 账号，在独立临时状态目录启动真实宿主、网关、签名与适配器。
模型为 `codearts/deepseek-v4.1-flash`，接口为流式 `/v1/responses`。
使用尚未过期的临时凭据，未调用账号续期。本文只记录耗时、状态和匿名账号代号。

## 复现与结论

默认配置下先串行发送 3 个短请求，再并发 2 个，随后并发 4 个。前三组正文首字约 0.81–1.30 秒。
最后一组出现以下结果：

| 请求 | 获取名额 | 正文首字 / 失败时间 | 结果 |
| --- | ---: | ---: | --- |
| four-0 | 0 秒 | 首字 0.880 秒 | 成功 |
| four-1 | 0 秒 | 首字 63.109 秒 | 成功 |
| four-2 | 0.922 秒 | 首字 64.258 秒 | 成功 |
| four-3 | 等待 15 秒 | 15.027 秒返回错误 | 本地队列超时 |

上游原始响应为 HTTP 400：

```json
{"error_code":"TM.00001041","error_msg":"并发会话数已达上限(3个)，请关闭部分会话后重试。"}
```

紧随其后的队列状态接口却返回 `status: "working"`、`queue_position: 0`。
原适配器在这个分支每隔约 10 秒重发同一请求，期间一直持有本地账号名额，直到约一分钟后恢复。
因此本次复现的主要等待发生在上游限制与内部重试，不能仅用本地获取名额的耗时解释。

单独复用 Chat-Id、单独复用 Session-Id、两者一起复用，以及设置 `Connection: close` 的对照中，
限制仍可出现，未采用这些改法。上游内部为何没有立即释放容量，及其他实例是否同时使用账号，
本测试无法确认；不把报文中的“3 个”解释成可持续的每分钟请求额度。

## 修复与复测

在传输边界复用依赖中已有的 `isConcurrencyLimitError()` 判定 HTTP 400/403，不再等队列状态确认。
被限账号的当前模型冷却 10 秒并释放名额，输出前可尝试其他账号；全部不可用时明确返回错误。
冷却期间的新请求同样得到排队错误，不再误报凭据缺失。普通参数错误不换号，也不冷却账号。
读取判定函数的模块位置与函数形状在 `src/core/upstream.ts` 统一核对，不复制供应商业务码解析。

| 场景 | 成功情况 | 正文首字或失败耗时 |
| --- | --- | --- |
| 默认配置，重复上述突发序列 | 正常请求成功；触限请求明确失败 | 触限请求约 1.182 秒结束，不再等待 63–64 秒 |
| 每号上限 2，两个账号同时各接 2 请求 | 4/4 成功 | 首字 0.755、1.045、1.045、1.126 秒；总耗时 0.848–1.300 秒 |
| 默认配置：长回答、同会话后续请求、另一会话并行 | 3/3 成功，绑定正确 | 同会话等待原号 1.674 秒；另一会话首字 1.141 秒，无需等待原号 |
| 账号 A 连续成功 3 次后，再用已有会话触发其上限，账号 B 可用 | 自动从 A 切换到 B 并成功 | 首字 1.279 秒，总耗时 1.396 秒，调度尝试数为 2 |

“快速返回错误”与“成功请求更快”是不同结果，表中分别列出。修复并没有增加华为服务端容量。
当所有账号的容量已耗尽时，增加本地并发上限仍可能触发服务端限制。

## 使用与范围

本次实测时默认值为 1；后续按用户要求，`CODEARTS_MAX_IN_FLIGHT` 默认已调整为 3，显式配置仍可覆盖。
`LOG_LEVEL=debug` 的 `[codearts-scheduling]` 日志包含获取名额、首个内容块、正文首字、总耗时与尝试数，
可用于区分本地排队、上游等待和先输出推理的情况。

这些结果来自短文本、小规模并发、预热后的目录；未覆盖线上转发面板的重试策略、持续满载、长上下文、
GLM 模型或用户原始请求正文，不能保证所有请求都达到相同首字耗时。已有会话的账号绑定与完整 SSE 名额管理保持生效。
